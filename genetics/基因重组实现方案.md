# 杂交整活基因系统 v2：实现方案（可实施草案）

日期：2026-09-24。用途：游戏基因判定、后代外观编译、Tripo 生成与验收。

**核心建议：基因决定“具体长什么”，Tripo 负责“把已经决定的外观建出来”。不要让 Tripo 自由解释“把 A 和 B 融合”。** 一次后代保留一个主体轮廓、一套完整表情，再加入另一方的一至两个辨识点。颜色可以很离谱，身份仍应一眼认出。

## 1. 已知事实、建议和未验证范围

- 用户已确定：有显性、隐性和不表达；需要可杂交、可整活、角色神似；游戏内部调用 Tripo；面数接近现有资产。
- 本次实测：`new model` 有 13 个 GLB，2272–6984 三角面；全部没有 skin 和 animation。不是 13 个都已进游戏，运行时可用性尚未验证。
- 本次交付：扩充基因表、13 个资产的结构化目录、离线重组参考代码、4096 次遗传模拟和示例后代数据。
- 本文的配额、概率、预算、显隐关系是**建议默认值**，并非用户已经批准的游戏数值。
- 本次没有调用收费生成接口，没有新杂交 GLB，也没有读到项目的实际 `index.html` / `GENE_DEFS`；旧表关于游戏当前状态的内容只作为历史记录。

## 2. 为什么旧 32 槽不够

旧槽能够描述“黄色、动物眼、有没有角”，无法描述粗框墨镜、粉中分头发、厚棕唇、巨大食指、红晕爱心瞳孔、无脖子肥胖人形、香蕉壳和刀盾组合。结果是两只动物都被编码为“黄色＋动物眼＋小四肢”，角色差异在送给模型之前就已丢失。

不建议简单追加很多布尔开关继续随机。正确补法是：**保留旧 32 槽作为兼容投影；新增有名字的角色特征组合、区域颜色和表达约束。** 两个系统只有一份权威数据：v2 基因型。旧 32 位数组是派生值，不能同时独立修改。

## 3. 三种概念必须分开

| 概念 | 示例 | 是否遗传 |
|---|---|---|
| 基因型 genotype | 身体色 `[yellow, green]` | 两个等位基因都保留，子代每个亲本各拿一个 |
| 表达结果 phenotype | 黄色，绿色这次被显性遮蔽 | 不能只拿这个结果当下一代父母基因 |
| 外观实现 artifact | 纹理中的黄色、具体 GLB 网格 | 不是基因型，不能从 GLB 反推出隐性基因 |

“不表达”不是第三种颜色。至少区分：

1. `none/none`：遗传上无该器官/装饰，不凭空生成。
2. `A/a`：a 被 A 的显性规则遮蔽，a 仍可传给下一代。
3. `structural_suppression`：例如纯球体没有握持锚点，刀盾基因暂不显示。
4. `identity_suppression`：爱心瞳孔是本次身份核心，深色墨镜会挡住它，因此墨镜本次不显示。
5. `budget_suppression`：装饰过多，为清晰度暂不显示；必须在 UI 说明“携带但未显现”。
6. `unknown`：资料不足，**不是 none，也不是隐性**。从入库流程阻止进入随机生成，待补资料。

基因型和被压制原因都保存。不能因为本代没有画出尾巴，就把尾巴从 DNA 中删除。

## 4. 推荐数据结构：成对等位基因 + 连锁组合

```json
{
  "schemaVersion": "gene-v2",
  "genome": {
    "body_plan": ["sphere", "round_bust"],
    "face_pack": ["heart_blush_tears", "sad_frog"],
    "body_color": ["yellow", "green"],
    "hair_pack": ["none", "medium_wavy"],
    "hair_color": ["none", "black"]
  },
  "homologOrder": ["parentA_gamete", "parentB_gamete"],
  "expressionSeed": 17,
  "rulesVersion": "gene-v2-draft-1"
}
```

`face_pack` 是一个完整、可遗传的性状组合，它内部存的是眼型、瞳孔、嘴型、红晕、泪痕和相对布局。**初版不要在组合内逐零件重组**。例如爱心瞳孔＋红晕＋波浪嘴一起传，悲伤蛙的垂眼＋厚唇＋眼下褶线一起传。

`hair_pack + hair_color` 同一个连锁块取自父母同一条同源染色体，避免“继承了无头发却孤立继承红发色”。后续可以添加小概率块内交换，但 v1 默认 0，先稳住辨识度。

`body_plan + body_scale` 也是一个连锁块。体型包含头身比例、是否无脖子、四肢布局、基本锚点；头不能独立抽成婴儿、躯干独立抽成蛇后再希望生成器猜对。

## 5. 显性、隐性和概率

### 5.1 不是“显性＝抽到概率高”

每个亲本各传一个等位基因，杂合亲本 A/a 传 A 或 a 各约 50%。显性影响的是拿到一对之后如何表达，而不是让 A 在减数分裂时有 90% 被传递。

若约定黄色 Y 对绿色 g 显性：

- `YY × gg` → 全部 `Yg`，全黄但携带绿。
- `Yg × Yg` → 基因型 1/4 YY、1/2 Yg、1/4 gg；黄色 3/4、绿色 1/4。
- `gg × gg` → 全绿。

这只是游戏规则示例；并不意味着现实颜色按这个规律遗传。已交付参考代码只明确设置了 yellow > green，其余不同颜色默认同级择一，便于之后配置。

### 5.2 多种互斥形态

`cat_eye` 和 `frog_eye` 不是简单大小写一对，不要把所有角色列成全局强弱排行榜。按“同一位点的等位基因对”配置：

- 已有显隐关系：按表选择，另一条潜藏。
- 同级：使用后代固定种子择一，出生后永久记录本代选择；刷新页面不再抽。
- 共显性：仅白名单允许，比如双色分区；初版不开放两种嘴型共显性，避免双嘴。
- 不完全显性：只用于受限数值，比如固定范围内的体型；不要平均混合整张脸。
- 可选器官：原型暂定 present > none。这可能令 F1 配件过多，所以必须配合可解释的表达预算。正式游戏应逐类审定显隐规则。

## 6. 一次繁殖的完整流程

```text
固定两个亲本基因型 + breedingEventId + 随机种子 + 规则版本
    ↓
亲本分别按连锁块取一条同源副本（各 50%）
    ↓
合并成子代成对等位基因；保留来源，不能从外观再生成 DNA
    ↓
逐位点计算显隐；同级按固定种子择一
    ↓
确定一个 body_plan 和一个完整 face_pack
    ↓
检查器官锚点、遮挡、配件位置、表情兼容性
    ↓
最多表达 2 个额外高显著特征；未表达项带原因留在 DNA
    ↓
形成唯一外观规格：轮廓＋表情＋关键改动＋区域配色＋禁项
    ↓
查缓存 / 判断是否仅局部可控编辑
    ↓
必要时先做一张统一子代参考图，再交给 Tripo 建模
    ↓
GLB 技术验收 + 身份锚点视觉验收 → 发布或待修复
```

所有“下调表达”只能影响 phenotype，不修改 genome。模型失败重试也不能重新抽基因。用户支付的是这一只已确定基因的后代，不是后台不断重抽直到能画出来。

### 6.1 控制“像谁”和“哪里抽象”

- 主体由最终表达的 `body_plan` 决定，不再额外从外部随机一个不在基因里的模板。
- 脸由 `face_pack` 决定，全套最多一张主脸；要换脸就整套换，不把鼻口独立打碎。
- 另一方至少应有一个**可见且区别于主方**的辨识点。仅“都是黄色”不算。
- 可允许某次遗传确实几乎像单亲；标记普通后代，不谎称强杂交。不应为了保证有梗偷偷增加不属于基因型的牛角。
- 如果玩法一定要求每次有明显双亲效果，需在交配前公开“表达偏向”选择或增加显式催化道具。不能事后暗改已经承诺的显隐概率。

### 6.2 位置与兼容表

| 情况 | 初版规则 |
|---|---|
| 完整球体＋刀盾 | 没有手锚点则刀盾潜藏；禁止生成器擅自长手。只有显式 `sphere_with_stub_hands` 体型能持物 |
| 球体＋西装 | 默认不适配；若要球面下半部西装，新增已验证的 `suit_lower_hemisphere` 适配器，不能等同人形上衣 |
| 爱心眼＋深色墨镜 | 若爱心眼是身份锚点，墨镜潜藏；或预先批准抬到额头的墨镜变体 |
| 牛角＋帽子＋花 | 每个锚点一个占用者；允许经过验证的侧移/缩小，否则较低优先级潜藏 |
| 犬鼻＋鸟喙 | 同属脸包，二选一，不随机叠加第二个嘴 |
| 香蕉壳＋猫脸 | 壳和面孔是不同语义区域，猫脸永远朝前；棱线不是随机污渍 |
| 巨大手指＋小西装 | 保留巨大手指这一比例异常，手臂/腿仍短；不能让重拓扑把手指缩成普通比例 |
| 墨镜遮眼 | 眼睛仍存在；eyeOn 不能因为被遮挡写成 no |
| 脸部照片＋改体色 | 避开脸部纹理，只染身体区域；否则红晕、猫眼和嘴型会被破坏 |

## 8. 13 个资产怎么建初代基因

推荐先把已观察性状初始化为 `X/X`。隐藏基因无法从 GLB 读取，不要宣称它们“本来携带了绿色/牛角”。

如果想让初代就有惊喜：在**策划配置**里为部分初代指定 `X/x` 隐性组合，并写清概率与来源。这是设计投放，不是检测结果。例如只给 20% 的黄豆设置 Y/g 携带者，另外 80% YY；百分比需平衡测试后再定。

JSON 中 `observed_phenotype` 是依据网格名、材质和预览做的**建议标签**；`production_ready=false` 不是模型错误，而是还没经过实际游戏验收。6 个 Tripo 资产只有一个网格，各局部锚点/区域遮罩还未分割，不能宣称它们已经可以直接换头换耳。

## 9. 颜色与材质：这次最容易翻车的部分

不要写“green frog mixed with emoji”。写“完整球形黄豆轮廓，只把身体底色改成绿色；爱心瞳孔、鼻脸红晕、泪痕和波浪嘴保持”。身体底色不影响粉色心形瞳孔、红嘴唇、白眼或蓝衣服。

每个资产后续补 `region_manifest`：`body_base / face_identity / hair / eye_white / pupil / blush / lips / outfit / gear`。当前多网格资产可借助 mesh/material 名半自动标注，但同一 material 可能跨多个部位，仍需检查。单网格的 6 个贴图资产要补 UV 遮罩或分割结果后才支持局部染色。

**fur、jelly、glossy 是不同维度。** 建议拆成 `surfacePattern=fur` 和 `renderFinish=opaque|softGloss|jelly`，后者先作为项目统一渲染规范，不默认加入遗传。六个 Jelly 文件的 alpha=0.95、roughness=0.18、BLEND 能证明“半透明配置”，不能证明有体积透射；还带 roughness 贴图，实际粗糙度不是处处 0.18。

## 10. Tripo 接入：先锁外观，再建模

### 推荐主流程

1. 后端根据基因生成结构化 brief，确定识别锚点和区域配色。
2. 优先复用可验证的已生成后代；局部换色/挂件有成熟遮罩和锚点时本地完成，不为每次变色重做整模。
3. 新轮廓组合先生成/制作**一只完整后代**的统一参考图。检查主脸、比例、道具数量，然后图生 3D。两张不同父母的图片不是同一角色多视图，不能直接当 multiview 的前后视图上传。
4. 后端提交任务；游戏显示孵化/生成中，不能承诺固定秒数。
5. 记录 task_id、请求版本、参考图 hash、种子和任务状态；轮询或 webhook 更新。下载 GLB 后重新计数与审查。
6. 必须在最终游戏发布环境验证一次加载、材质、朝向、尺寸和整体现有运动，再开放批量。

### 当前官方文档核对（2026-09-24）

P 系列 v3 文档列出 `POST /v3/generation/text-to-model`，参数名 `model`，P1 示例为 `P1-20260311`；有 `face_limit`、`texture` 和 `pbr`。不要把旧 v2 的 `model_version` 请求体混用到 v3。

建议初版使用已选定且验证过的 P1、4500 面预算、贴图和 PBR；这是适配器建议，不是本次已成功提交的请求。若走图生流程，使用对应 image-to-model 文档定义上传输入，不能将这里的 text 请求体原样复用。

```json
{
  "model": "P1-20260311",
  "prompt": "One unified round green emoji creature. A complete spherical body. Keep large wet eyes, pink heart pupils, pink cheek and nose blush, a tiny wavy smile and tear streaks. Body base green only; keep facial colors unchanged. Full object, no text, game-ready stylized textured mesh.",
  "face_limit": 4500,
  "texture": true,
  "pbr": true,
  "model_seed": 17001,
  "texture_seed": 17002
}
```

来源：[P 系列生成文档](https://developers.tripo3d.com/en/docs/generation-text-to-model/p)、[图生模型文档](https://developers.tripo3d.com/en/docs/generation-image-to-model/standard)。以具体已选接口的契约测试为准；本次没有账号权限、耗时或费用实测。

### 任务与缓存

`childId` 在提交前确定；写入持久队列，用本地唯一键锁住一个 child 的一次提交。超时结果未知时先根据已保存 task_id 查询，不直接重复扣费提交。只在任务明确失败且达到退避条件时重试；建议 1 次自动修复，仍失败展示已保存基因并转人工，不无限生成。

缓存键建议包含 `phenotypeCanonicalJSON + rulesVersion + promptCompilerVersion + referenceHash + modelVersion + textureVersion + faceLimit + allSeeds + normalizationVersion`。外观相同的不同 DNA 可以共用 GLB，但两只宠物的隐性基因记录不能合并。缓存只命中技术及视觉验收通过的结果。

## 11. 面数与身份验收

- 当前实测中位数 2982；有 4 个资产超过 4500，最大 6984。因此建议普通后代目标 3000–4500，复杂脸/刀盾类允许到 7000。硬上限待游戏性能测试确认，不能宣称已满足帧率。
- 身体基础轮廓、嘴唇/鼻口、角、重要道具需要几何；毛色、虎斑、腮红、细皱纹优先纹理。心形瞳孔可以贴图，但必须在游戏实际屏幕尺寸看得出爱心。
- `face_limit` 是生成请求，GLB 回来必须按三角面再统计，不相信文件名里的 Face3000。比如 Fengou 实测 3026。
- 技术检查：可解析 GLB、单位/坐标统一、外部贴图可达或内嵌、无 NaN、明显穿插检查、贴图大小/材质数量/透明排序、模型底部与重心。多零件相交不等于一个连续封闭可打印实体。
- 视觉通过条件建议：主体轮廓正确；主脸锚点至少 3 个可认；目标借入的辨识点至少 1 个可见；不得重复头、重复嘴；禁止把香蕉棱线画成随机脏污或把巨大手指变回小手。
- 身份通过不能靠 count 或脚本字符串检查。以固定前/侧/后视图、游戏实际缩略大小和实际场景截图审查；MVP 先人工打勾，后续再评估视觉模型评分。

## 12. 三个具体例子

### A. 绿色爱心黄豆

主体 sphere、脸 heart_blush_tears、体色 green；爱心粉、腮红红、眼白白保持。可来自二代绿等位基因显现。若明确要“牛＋黄豆”，必须再有牛来源角/鼻等基因；单改绿不能命名为牛杂交。牛 GLB 不在 new model 中，需要从旧资产库找来复核。

### B. 红头发西装老头

体型 `stocky_no_neck_chibi`＋脸 `wide_open_mouth_man`＋西装＋巨食指为底座，发型换 `medium_wavy`、发色 `red`；小四肢和无脖子锁住。这个老头和 red 发色初代都尚未在本次 13 项中启用；必须作为候选入库或明确突变等位基因。不能假装在现有目录随机杂交就一定得到。

### C. 香蕉壳爱心猫

主体 banana_upright，脸只能选 photo_kitten 或 heart_blush_tears 一个。想要“猫脸上有爱心瞳孔”需新增**经过美术验证的** face adapter `kitten_heart_eyes`；不是把两个脸包平均叠上。保持香蕉柄和纵向棱线，身体黄色不染掉猫脸。

## 13. 最短落地顺序

1. 先确认 13 条资产命名/身份，修正 Fenxiang 的猪鼻外观歧义；补齐牛和老头的资产引用。
2. 把旧表的“显式已知”和“默认占位 latent*”分开。新初代默认纯合；策划明确配置少数隐性携带者。
3. 后端接入 v2 基因型与固定种子；使用参考代码核对遗传结果，实际游戏实现仍需加持久化、事务和接口层。
4. 先验证三个配方：黄豆换绿、卷发换色、已有体型加墨镜。它们能分别暴露染色、身份和遮挡问题。
5. 再做有体型变化的混合，并用统一子代参考图交给 Tripo。
6. 实际发布环境验收一只，再批量开放繁殖。
